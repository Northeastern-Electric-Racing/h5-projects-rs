# Atlas CAN bootloader

CAN bootloader with per-ECU configuration, platform-specific hardware support,
and firmware update, confirmation, and rollback support.

## Layout

- `ecus.json`: ECU CAN IDs, hardware selection, and platform memory layouts.
- `config.rs`: build-time JSON parsing and validation.
- `tools/`: host build and probe helper.
- `platforms/`: platform-specific bootloader implementations and build scripts.
- `app/`: application library for boot confirmation and bootloader requests.

## Build and flash

Run from this directory, replacing `<ecu>` with a name from `ecus.json`:

```sh
cargo build-atlas <ecu>
cargo download-atlas <ecu>  # Build, download, and reset through probe-rs.
cargo run-atlas <ecu>       # Build and run with probe logs.
```

Install `probe-rs` for download/run. Firmware outputs go to
`../target/<ecu>-bootloader/<rust_target>/release/<cargo_package>`.
Files included from `OUT_DIR` are generated by the platform's `build.rs`.

## Application integration

Add `atlas-app = { path = "../atlas/app" }` to an application at the repository root.
Link the application at its JSON `memory.application` address and reserve the DFU
and state regions. Flash the bootloader separately before using CAN updates.

The application owns CAN initialization, filters, bitrate, and receive task. Allow
its configured `application_boot_request_id` through the filter. Pass received
frames to the helper from task context:

```rust,ignore
// Supply the platform's state partition and an aligned flash-write scratch buffer.
let state = atlas_app::BlockingFirmwareState::new(state_partition, scratch.as_mut());

let request = atlas_app::BootRequest::for_ecu(ecu_name).expect("ECU must exist in ecus.json");
// Use request.id() when configuring the application's CAN filter.
let mut bootloader = atlas_app::Bootloader::new(state, request);

bootloader.confirm_boot()?; // Call after application startup checks pass.
// In the existing CAN receive loop, before normal message dispatch:
bootloader.handle_frame(&frame)?;
```

The library's `build.rs` generates request settings from `ecus.json`; select the
ECU by name without copying CAN IDs or payloads. Unknown names return `None`.
No ECU environment variable is needed for application builds.

Create the state partition using the platform's flash driver and `memory.state`
layout. Partition offsets are relative to the backing flash region. Match the
scratch buffer's size and alignment to the driver's flash-write requirements.
Keep the flash owner, synchronization objects, and scratch buffer alive while
using the helper. Handle returned flash errors in the application; failed requests
do not reset the processor.

## Update flow

1. A valid application starts immediately unless a bootloader request is persisted.
2. A matching application CAN request records DFU mode and resets.
3. The host contacts the bootloader, uploads into DFU, verifies CRC, and activates.
4. On reset, the bootloader copies/swaps the staged image into the application region.
5. The new application confirms startup; otherwise the next boot rolls it back.

## Adding hardware

Add an ECU entry referencing an existing platform for another board using that
platform. For another MCU, add a crate under `platforms/` and its platform entry
in JSON. Keep peripheral and flash details in that crate; extract shared runtime
logic when a second implementation needs it.
